# Week2 GUIDE · Planner / 记忆压缩 / 单 Agent 0.1 怎么写的

> 理论对应：hello-agents 第四章 Plan-and-Solve 节、第八章记忆节；卡码网第三节 1.规划、2.工具。
> 本周产出 = 项目第一个"能演示的东西"：输入一个模糊目标 → 输出带数据的分析报告。

## 文件地图

| 文件 | 干什么 | 关键设计 |
|---|---|---|
| `tools.py` | 工具换真实 CSV 数据（pandas） | 与 week1 接口完全一致 → 业务换数据，Agent 零改动；底部自带自测 |
| `planner.py` | 目标 → 子任务 DAG（JSON） | 一次拆完（Plan-and-Solve）+ JSON mode + 字段校验 + Reflection 重试 1 次 |
| `memory.py` | 会话记忆 + 超长自动摘要压缩 | 滑窗（近 N 条原文）+ running summary（旧消息 LLM 压缩） |
| `agent_v01.py` | 串起来：拆→执行→汇总 | 每个子任务 = 一次 ReAct 循环；依赖结论显式传递 |

## Planner 的三个设计点（面试深挖区）

1. **为什么一次拆完（A）而不是边做边拆（B）**：省 token、计划可人工审阅、无依赖子任务将来可并行；
   B 灵活但贵且不可预测。生产做法：A 出骨架，B 在子任务内部执行（Week4 就是这个结构）。
2. **怎么保证输出合法 JSON**：`response_format=json_object`（采样级约束）＋ 我们的字段校验
   （id 唯一、依赖只指向更小 id=无环、task_type 枚举）—— 模型约束 + 程序校验双保险。
3. **Reflection 重试**：解析/校验失败时，把模型自己的输出和错误信息喂回去重写一次。
   "失败不是人工修，是让模型看着错误自己修"——这正是 Harness 思想（Week4 系统化）。

## 记忆压缩（memory.py）

```
每轮请求的 messages = [system] + [历史摘要(≤200字)] + [最近6条原文]
```
- 触发时机：被挤出滑窗的旧消息累计字符数 > max_old_chars（= 上下文预算的执行点）；
- 压缩方式：LLM 把旧消息 + 已有摘要滚动合并成新摘要（保留：需求/关键数字/未解决问题）；
- 为什么不全程摘要：近期对话信息密度最高，必须保原文；远期才值得压。

## agent_v01.py 的数据流

```
goal → plan() → [任务1(无依赖), 任务2(无依赖), 任务3(depends_on=[1,2])]
                 ↓ 逐个执行（id 升序即拓扑序，planner 已校验）
   任务1 的结论以文本注入 任务3 的 prompt（显式状态传递，替代框架的 shared state）
                 ↓
   Aggregator：汇总所有结论 → 报告（冲突必须点名）
```

## 必须弄懂的 5 个点

1. **子任务依赖怎么定**：数据查询先行、综合殿后；依赖只能指向更小的 id（天然无环）。
2. **为什么长对话要压缩**：窗口有限 + 注意力稀释 + token 成本，三选一都足以立项。
3. **工具结果进上下文的度**：只返回统计和样例（samples[:5]），不整表灌入——工具返回值也是上下文工程。
4. **子 Agent 失败怎么办**：本周简单抛错；Week4 升级成重试+超时+降级护栏。
5. **评测意识萌芽**：从本周起每个 demo 都打印 token 消耗——没有数字就没有优化。

## 面试追问预案

- "Planner 拆错了怎么办？" → 重拆（Reflection）+ 子任务内部 ReAct 兜底 + 评测集统计拆解错误率。
- "多轮记忆为什么不用向量库存？" → 教学规模滑窗+摘要够用且零依赖；用户画像类长期记忆才需要向量库（Week4 提及路线）。
