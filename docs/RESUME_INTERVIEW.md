# ShopPilot 简历面试拷问手册

> 简历 ShopPilot 段落涉及的每个专业术语 → 是什么、为什么这么设计、面试官怎么拷问、你怎么答。
> 按简历原文顺序组织，每个术语一节。能背下来直接应对。

---

## 简历原文（背熟这三行）

**主要内容**：电商导购智能体，结构化抽取需求后并行查询商品池、口碑与售后知识库，输出带依据的推荐卡、对比卡与避坑提示；支持多轮槽位继承（买耳机→顺带买充电线自动识别配套），跨会话记住偏好。

**核心设计**：自主搭建三部件编排（规划拆任务 DAG → 执行分层并发 ReAct → 成稿聚合 + 五项确定性自检）与两层记忆（会话滑窗摘要 + 跨会话 Markdown 长期记忆）；推荐为七维加权打分（含物流时效）在工具内确定性计算；售后走 RAG 混合检索（TF-IDF+BM25+RRF 融合）强制引用溯源。

**项目成果**：同题库纯 API 直调任务完成率仅 48%（编造价格、该拒未拒），Agent 达 100%；27 题验收集任务完成率/工具命中率/拒答正确率均 100%，引用可验证率 96%；工具按任务类型预加载较全量注入节省 16-28% token。

## 一、主要内容区术语

### 1. 结构化抽取需求（ShoppingQuery）

**是什么**：用户输入自然语言后，Planner 第一步把它抽成结构化 JSON——意图（recommend/compare/review/after_sales/research/out_of_scope）、实体（商品名列表）、品类、预算上下限、在意维度（concerns）。用 `json_object` 强制合法 JSON，再过 Pydantic 契约校验。

**为什么这么设计**：
- 不结构化 = LLM 自由发挥，同一句"500以内耳机"每次拆出的子任务都不一样，无法回归
- 用 Pydantic `field_validator` 在入口清洗脏数据，下游所有模块拿到的永远是干净对象

**拷问**：
- *"LLM 输出的 JSON 经常不合法怎么办？"* → json_object 强制采样约束 + Pydantic 校验失败时把错误喂回让它重写一次（Reflection 重写），两步兜底
- *"意图分类错了怎么办？"* → 加了"防误拒闸"：Planner 判 out_of_scope 但文本明显是导购请求时，用确定性规则（关键词命中）触发重问一次，零 token 成本

### 2. 并行查询商品池 / 口碑 / 售后知识库（DAG 分层并发）

**是什么**：子任务拆成 DAG（有向无环图），按拓扑分层，**同层无依赖的任务用 ThreadPoolExecutor 并发执行**。比如对比两个商品时，查 A 的工具和查 B 的工具同时跑。

**为什么这么设计**：
- 串行跑对比题要两轮工具调用的时间，并行只要一轮
- DAG 保证有依赖的任务（先筛商品再查口碑）不会乱序

**拷问**：
- *"并行工具调用顺序乱了怎么办？"* → tool_call_id 机制：模型一次返回多个 tool_calls，执行结果按 `tool_call_id` 一对一喂回，顺序乱但 id 对应不乱
- *"为什么不用 LangGraph 做 DAG？"* → 我们的 DAG 只有拓扑分层并发这一个需求，手写 20 行就能实现，引入 LangGraph 反而是负担

### 3. 多轮槽位继承（配套识别）

**是什么**：用户先说"预算500推荐降噪耳机"，下一轮说"顺带买个充电线"——系统不重新推荐耳机，而是把 entities 抽成 `["蓝牙耳机A","数据线E"]`，预算和在意维度继承上一轮，识别为配套场景。规则写在 Planner prompt 第8条。

**为什么这么设计**：
- 真实电商场景大量是"买完主件配配件"，如果每次都从零开始，用户体验像失忆
- 但**不做自动推断画像**（比如不猜"用户是学生党"），只继承用户明确说过的预算/在意维度——推断错一次就翻车

**拷问**：
- *"怎么判断是配套还是新需求？"* → 关键词规则（顺带/顺便/除了X还得配个/充电线这种配件词）+ 记忆块里最近提到的商品名，Planner prompt 里显式规定继承哪些字段
- *"为什么不做用户画像自动推断？"* → 推断错一次（把"给爸爸买"推断成"用户自己要"）信任就崩了；只记用户明确表达过的，且本地 Markdown 可一键删

### 4. 跨会话记住偏好（长期记忆）

**是什么**：长期记忆落盘成 `data/memory/{user}.md`（Markdown 追加式），每轮对话结束追加一条：问了什么、答了什么、涉及哪些商品、结论要点。下次对话时按关键词命中检索最相关的几条注入 Planner。

**为什么这么设计**：
- 不上向量库：条目量级在几十条内，jieba 分词 + 关键词命中已经够用，向量库是过度工程
- Markdown 人可读：用户能直接打开看、能删，比黑盒向量库可信

**拷问**：
- *"长期记忆会不会脏？"* → 写入过筛四问：是否长期稳定（"我今天想爬山"不写）、以后是否有用、是否用户明确表达、隐私合规（本地可删）

## 二、核心设计区术语

### 5. 三部件编排（规划→执行→成稿）

**是什么**：运行时只有三个部件，刻意收敛——
- **规划**（planner.py）：意图/约束抽取 + 拆子任务 DAG
- **执行**（executor.py）：子任务按拓扑分层并发；data/review 类走有界 ReAct 循环，knowledge 类走 RAG
- **成稿**（composer.py）：聚合子结论 → 结构化产出卡 + 强制引用 + 五项自检

**为什么这么设计**：
- 早期拆成8层（config/llm/models/harness/agents/前端），那是把每层都拆开写的结果；重构成熟版后刻意收敛，运行时就这三个部件
- "不为分层而分层"——分层的唯一衡量指标是"换业务要改几层"，现在换业务只改 domains/ 一层

**拷问**：
- *"你这不是 DeerFlow 复现吗？"* → 承认范式同源（Planner/Dispatcher/Aggregator），但差异在：业务深度（7个电商工具真实跑通）、确定性 Reflection（DeerFlow 没有纯函数自检）、三层记忆（DeerFlow 不做配套继承）、评测闭环（27题四项指标回归）
- *"为什么不用多智能体？"* → 电商导购是窄域任务，三个部件足够；上多智能体（>3个角色）是调试地狱，错误累积放大

### 6. 有界 ReAct 循环（三重预算）

**是什么**：ReAct（思考→调工具→观察→再思考）循环加三重预算护栏——max_steps（最多8步）、max_tokens（6万）、max_cost_cny（0.5元），任一超限即降级返回，不无限烧钱。加退避重试、超时降级、输出校验钩子。

**为什么这么设计**：
- 没有护栏的 ReAct 会无限转圈（模型反复调错工具）
- 降级不是报错，而是返回兜底文案 + degraded 标注，其他子任务继续

**拷问**：
- *"步数超限了用户看到什么？"* → 返回"已达最大步数，任务未完成，请基于已有信息回答"，前端标注⚠️降级
- *"LLM 调用失败怎么办？"* → 指数退避重试2次（0.5s/1s），仍失败才降级

### 7. 五项确定性自检（Reflection）

**是什么**：成稿阶段用五条纯函数规则检查（零 token），不过关触发一次 LLM 修复——
1. **引用可验证**：答案里的 [n] 编号必须落在资料编号范围内
2. **预算约束**：推荐卡内价格 ≤ 用户预算上限
3. **商品溯源**：卡内商品名必须出现在工具返回或用户原文中
4. **误拒答**：售后场景检索到资料却回答"没有相关资料"
5. **目标覆盖**：用户点名的商品必须出现在回答里

**为什么这么设计**（面试核心）：
- LLM 自评有**自我讨好偏差**（自己给自己打高分），让它自查不可靠
- 这五条都是数学题（编号越界/价格比较/字符串包含），规则判断 100% 可靠、可回归、零 token
- LLM 只在规则判失败后负责"修"，不负责"查"

**拷问**：
- *"为什么不用 LLM-as-judge？"* → 裁判有偏差且烧钱；引用越界、价格超预算这类错误用规则判 100% 可靠，语义类才用 LLM
- *"这五条怎么保证不漏？"* → 每条都能对应一个真实翻车案例（比如引用编号越界就是因为模型编造来源），badcase 驱动加规则

### 8. 两层记忆（会话滑窗摘要 + 跨会话 Markdown）

**是什么**：
- **短期**（ShortTermMemory）：最近6轮原文进滑窗，更早的由 LLM 压成≤150字滚动摘要
- **长期**（LongTermMemory）：跨会话 Markdown 文件，关键词命中检索

**为什么这么设计**：
- 长对话变傻是三大原因：上下文窗口限制、注意力稀释、token 成本；滑窗+摘要解这个
- 不做 MemGPT 式 LLM 自管记忆——经常丢关键实体，显式槽位+滑窗更稳

**拷问**：
- *"摘要压缩什么时候触发？"* → 超出 keep_recent（6轮）时，把最旧的一轮压进滚动摘要
- *"为什么不用向量库存长期记忆？"* → 条目几十条量级，jieba 关键词命中已够用；向量库是过度工程，且用户不可读不可删

### 9. 七维加权打分（含物流时效）

**是什么**：推荐不是"按评分排序"，而是工具内做七维加权打分——
价格贴合 13% / 平台评分 16% / 评论均分 10% / 销量热度 8% / 好评匹配 22% / 差评风险 18% / **物流时效 13%**（次日达=1.0，4天=0.25）

输出带：总分 + 分项得分 + 好评/差评原文 + decision_reason 草稿。

**为什么这么设计**（面试核心）：
- 排序是数学题，让 LLM 算会算错还会编分；打分放工具内可回归（改权重 benchmark 跑一遍就知道好不好）
- 物流时效是电商转化关键信号——用户说"急用"时它直接主导排序
- LLM 只负责"讲"（把 decision_reason 组织成自然语言），不负责"算"

**拷问**：
- *"权重怎么定的？"* → 好评匹配最高（22%）因为"买耳机就是要降噪"比"评分4.5"更有说服力；差评风险次之（18%）因为退货率主要由差评驱动；物流时效13%是电商场景独有的
- *"为什么让 LLM 打分不行？"* → 同一批商品两次打分 LLM 可能给出不同排序，不一致；规则打分永远一致可回归

### 10. RAG 混合检索（TF-IDF+BM25+RRF）

**是什么**：售后问题走 RAG——
- **切分**：按 Markdown 标题结构感知切分（不硬切断段落）
- **向量路**：TF-IDF char n-gram（离线秒建、中文友好）→ 余弦相似
- **BM25 路**：jieba 分词 + BM25Okapi（对型号/数字/专名极准）
- **融合**：RRF `score = Σ 1/(60+rank)`，两路都命中的 chunk 排最前

**为什么这么设计**：
- 纯向量懂语义但怕专名数字（"鼓包""发票"召回差）；纯 BM25 反之；RRF 融合两头吃
- 强制引用溯源：售后答错=客诉，每个结论必须标 [n] 来源

**拷问**：
- *"为什么不用 bge-small-zh？"* → 小规模（5篇文档几十个chunk）TF-IDF 已够；换 bge 只需实现 encode() 接口，检索/问答代码零改动——可插拔设计
- *"RRF 为什么 k=60？"* → 工业界默认配置，经验值；作用是压低单路排名优势，让两路共识chunk排最前
- *"知识库里没有的问题怎么办？"* → 系统诚实说"知识库中没有相关资料"，不硬答

## 三、项目成果区术语

### 11. 纯 API 直调完成率 48% vs Agent 100%

**是什么**：同 27 题题库跑两遍——
- **纯 API 基线**：直接问 LLM（system=通用导购助手），不给工具、不给知识库、不拆任务、无记忆
- **Agent**：完整跑 Planner→执行→成稿全链路

**基线翻车实录**：推荐类5题全灭（编造"华为 FreeBuds 6i 约399-499元"）、拒答类4题全硬答、售后数字靠猜。

**为什么这么设计**（面试核心）：
- 回应"你不就是调 API 吗"——API 解决"会说"，Agent 解决"系统做对"
- 用约 15 倍 token 买的是**不编造、可溯源、该拒就拒**

**拷问**：
- *"48% 是不是你故意把基线写差？"* → 基线就是裸 LLM，没有商品池可查、没有知识库可引、没有意图分类；它的失败（编造价格、该拒未拒）是 LLM 的固有缺陷，不是我选的题难
- *"15倍 token 值得吗？"* → 导购场景答错=客诉/退货，token 成本（几分钱）远小于一次客诉成本

### 12. 27 题验收集 + 四项确定性指标

**是什么**：自建 27 题导购验收集（对齐字节 llmeval schema），四项指标全部**确定性规则判定、零裁判 token**——
- **任务完成率**：无降级 + constraints 全过 + 拒答行为正确
- **工具命中率**：实际工具集合对 expected_tools 的覆盖率
- **拒答正确率**：expected_behavior 与实际行为一致
- **引用可验证率**：答案 [n] 全部落在资料编号范围内

**为什么这么设计**：
- 评测集字段设计（id/prompt/reference/constraints/meta.expected_tools）与 bytedance llmeval 同源
- 不用 LLM 裁判：裁判有偏差且烧钱；四件事规则判 100% 可靠、可回归

**拷问**：
- *"27 题是不是太少？"* → 教学项目聚焦五大场景（推荐/对比/口碑/售后/拒答），每题都能对应一个真实 badcase；生产环境会扩到 100-300 题，但结构不变
- *"constraints 怎么设计？"* → must_contain（AND）/ must_contain_any（OR，兼容"12个月/一年"表述差异）/ must_not_contain（禁编造超预算商品）

### 13. 工具按任务类型预加载省 16-28% token

**是什么**：不是把全部 7 个工具 schema 塞进上下文，而是先由 Planner 判断任务类型（data_query/review_analysis/knowledge_qa/synthesis），只把相关工具 schema 注入——
- data_query → search_products / get_product_info / query_sales_rank
- review_analysis → query_product_reviews / search_reviews
- knowledge_qa → 无（走 RAG）
- synthesis → 无（纯推理，防乱调）

**为什么这么设计**：
- 工具 schema 是上下文里的固定开销，无关工具不进上下文 = 省 token + 降低模型选错工具的概率
- --compare 实验：同一题库跑两遍（预加载 vs 全量注入），平均省 16-28%

**拷问**：
- *"怎么保证任务类型判断不错？"* → Planner 判断错误时有 Replan 兜底（子任务 degraded → 带失败证据重拆）；且工具选错时工具返回结构化错误让模型自我纠正
- *"这个数字怎么测的？"* → benchmark.py --compare，同一题库同一 seed 跑两遍，avg_tokens 对比

## 四、可能被深挖的通用拷问

| 拷问 | 答法 |
|---|---|
| 不就是调 API 吗？ | `llm.py` 不到100行，其余是重试退避/超时降级/Replan/确定性自检/记忆/评测。基线实测 0.48 vs 1.00 |
| 和复现品区别？ | 承认范式同源；差异：业务深度、可解释记忆、确定性 Reflection、评测闭环、MCP 三原语，逐条有数字 |
| 幻觉怎么治？ | 生成侧强制引用+不足拒答；校验侧五项规则；评测侧引用可验证率 |
| 为什么不用 LangChain？ | 依赖越少每层越讲得清；换业务只改1层（adapter），预加载/确认闸这类定制能力框架里反而要绕着写 |
| 数据是自己造的吗？ | 是教学仿真数据（人工设计），理由：可控构造 badcase、可复现、无合规风险；换真实数据四步改法见 PROJECT_GUIDE §3.8 |
| 为什么不上多智能体？ | 电商导购窄域任务，三部件足够；上>3角色是调试地狱，错误累积放大 |
| 为什么不上向量库？ | chunks 几十条量级，jieba 关键词命中已够用；向量库是过度工程 |
| 为什么不做用户画像推断？ | 推断错一次（给爸爸买→用户自己要）信任就崩；只记用户明确表达过的 |

## 五、一句话收尾（面试结束时主动说）

> "这个项目的价值不是用了 LLM，而是用工程把 LLM 的不稳定性关进了笼子。七维打分让推荐可回归，两层记忆让多轮不断片，混合检索让售后不答错，确定性 Reflection 让编造无处遁形。每个决策都能回答'为什么这样设计、被否掉的方案是什么、换真实业务时改哪里'。"
