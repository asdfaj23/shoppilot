一、架构设计原因（每个取舍都写了被否掉的方案）

1.1 总体形态：8 层单向依赖

①config ②llm ──► ③models(Pydantic 契约) ──► ④harness/loop ⑤tools ⑥memory/observability
                                          └──► domains/ecommerce(6工具) + rag(FAISS+BM25+RRF)
    ⑦agents(planner→dispatcher→aggregator→reflector→team) ──► ⑧app.py / benchmark.py / mcp

分层单向依赖的意义：models.py 是全项目"普通话"，谁都可以 import 它，它不 import 任何人； 数据换源只动 adapter.py，换 LLM 只动 llm.py，换记忆存储只动 memory.py 的 load/save 两行。

1.2 三种 Agent 范式怎么组合（kamacoder《ReAct、Reflection、规划执行》）

文章结论"真实项目组合使用：先规划，中间 ReAct，交付前 Reflection"，本项目的落地：

范式落点工程护栏
规划执行（先拆任务防跑偏）Planner 一次调用产出 ShoppingQuery + 子任务 DAGPlan 是可更新的任务清单：子任务降级 → Replan 带失败证据重拆补救任务（换路径），最多一轮防循环
ReAct（路径不确定的执行）harness/loop.py 有界循环文章点名"ReAct 会跑散"→ 三重预算(steps/tokens/cost) + 同 goal 结果缓存 + 工具按 task_type 预加载（无关工具不进上下文，防误调又省 token）
Reflection（交付前检查）Reflector 五项自检文章强调"不是再想想，是按明确标准检查"→ 全部确定性规则（引用编号越界/超预算/库外编造/误拒答/目标覆盖），LLM 只负责修复这一步

1.3 记忆四分类（kamacoder《Agent 的记忆》）

文章核心："该记的记住，该查的去查，该忘的忘掉，该确认的确认"，四种记忆不能混在一层：

类型实现设计要点
短期记忆WorkingMemory 滑窗+滚动摘要"摘要压缩而非全文保留"：只留目标/约束/关键证据，丢掉已证伪方向等噪音
Session State结构化任务状态 JSON不是聊天记录：goal/意图/任务清单(含降级)/关键结论，下一轮注入 Planner 消解指代
长期记忆PreferenceMemory 画像文件写入像数据库：只写确定性抽取的用户明确表达；冲突=覆盖更新；条数上限=噪音清理；forget()=遗忘机制；带 updated_at
外部知识库shoppilot/ragRAG 是"可查的资料"，不是"对用户的记忆"——语义上分开，都是向量检索但用途不同

1.4 MCP 三原语（kamacoder《MCP 协议》）

MCP 是应用侧接入协议，Function Calling 是模型侧调用机制——不互斥：Host 经 MCP tools/list 发现工具，再转成 FC 格式给模型选。Server 按三原语暴露： Tools（6 个只读导购工具，共享 ToolRegistry——内部 Agent 与外部宿主调同一份实现）、 Resources（shoppilot://products 商品池、shoppilot://knowledge/{doc} 售后文档——"能看什么"，避免全塞 Prompt）、 Prompts（导购模板："怎么做更稳"）。安全边界在 Host：工具最小暴露、文件资源防目录穿越、参数 Pydantic 校验、危险工具确认闸。

1.5 其余关键取舍

  • Plan-and-Solve 而非纯 ReAct：token 省、计划可审、同层可并行；代价是需 Replan 补动态性（已实现）；
  • 同层 ThreadPoolExecutor 并发：推荐/口碑两路查询时延近半；
  • 结构化产出卡：Aggregator 输出 Recommendation/CompareCard/CaveatList JSON（被否方案：自由 markdown——前端无法渲染卡片）；
  • 清洗收敛到数据入口：Pydantic field_validator 修 LLM 脏 JSON（被否方案：每个使用点手写清洗）；
  • 拒答短路 + 双重防误拒护栏：out_of_scope 不拆任务省往返；误拒由"导购关键词复核 + 库外实体闸"两个零 token 确定性规则兜底。

二、"这不就是复现 DeerFlow / hello-agents？"——应对专节

这是最可能被问到的质疑。回答分三层：承认共同骨架 → 指出复现品没有的东西 → 用可验证证据收尾。

第一层：承认方法论同源。
Planner→Dispatcher→Aggregator 的三模块骨架确实来自 DeerFlow 范式（week4 教学代码已实现串行版）， 我不把"用了公开的架构范式"当创新点——就像 Web 项目用了 MVC 不叫创新。
第二层：以下五件事是 DeerFlow/hello-agents 没有或没做全的。
#差异点复现品现状ShopPilot
1业务深度通用研究/问答 demo，无领域工具链导购五场景各有专属工具与结构化产出卡（推荐清单卡/对比维度表/避坑清单），工具按 task_type 预加载
2可解释记忆多数只有会话 buffer 或提示词内记忆四类记忆分层（含 Session State 结构化状态），画像文件态持久化、前端可编辑、每轮明示"本轮记住了什么"——用户可验证、可纠正、可删除
3交付前 Reflection反思多为一句话提示词（"再想想"）五项确定性规则自检（引用编号/预算约束/商品溯源/误拒答/目标覆盖），LLM 只做修复——零裁判 token 可回归
4评测闭环论文复现项目普遍无效果测试25 题验收集 + 四项确定性指标（任务完成 1.0/工具命中 1.0/拒答正确 1.0/引用可验证 0.96）+ 工具预加载 token 对照实验
5MCP 三原语通常只包一层 function toolsTools/Resources/Prompts 全暴露，与内部 Agent 共享同一 ToolRegistry（单一事实源），安全边界显式设计
第三层：证据收尾。
"复现是学习手段不是目的，项目里每层都留了决策记录（docs/DESIGN.md），哪些是继承、哪些是 自研补强、被否掉的方案是什么，都写清楚了；效果有 25 题确定性指标可复现—— python benchmark.py --run 一条命令验证。"

四、面试深挖 Q&A（按追问深度排序）

Q1 messages 里没有 tool_calls 就停，为什么？
finish_reason=stop 表示模型认为信息足够进入作答；tool_calls 存在则观察结果必须按 tool_call_id 喂回再循环。messages 就是 Agent 的记忆，每一轮全量喂回去。
Q2 并行 tool_calls 顺序乱了怎么办？
结果按 tool_call_id 对应喂回，顺序无关——这正是 tool_call_id 存在的意义。 我的 loop 用线程池并发执行同一轮所有调用，返回后逐 id 回填。
Q3 为什么工具 schema 要 Pydantic 自动生成？
单一事实源：函数签名+参数模型写一遍，OpenAI schema 派生生成；改参数不再双写。 顺带拿到 Pydantic 校验：模型传脏参数在入口被拦，错误结构化喂回让它自纠。
Q4 工具预加载省了多少？
Dispatcher 按 task_type 只注入相关 schema（如 data_query 只给 4 个而非 6 个工具）。 benchmark.py --compare 输出同题库两遍的 tokens 对照——数字来自 trace， 不拍脑袋。
Q5 长对话为什么"变傻"，你怎么解决？
上下文污染+窗口限制+计费三重原因。滑窗保最近 6 条原文，更早的 LLM 压成滚动摘要； 再往上，结构化 Session State 保存 goal/任务清单/关键结论，比聊天原文更抗噪。
Q6 记忆怎么防"变脏"？
写入只收确定性抽取的用户明确表达（不信模型自由发挥）；冲突即覆盖（预算档变了就是变了）； 条数上限防噪音堆积；forget() 提供删除；updated_at 支持过期判定。 向量库只是检索层，不等于记忆设计。
Q7 RAG 为什么混合检索？
向量懂语义但对型号/数字不敏感，BM25 反之；RRF 倒数排名融合两路。Embedding 用 TF-IDF 字符 n-gram（离线秒建中文友好），Embedder 是接口，换 bge 只改一个类。
Q8 RAG 幻觉怎么治？
生成侧：prompt 强制 [n] 引用、资料不足明确拒答；校验侧：Reflector 确定性检查每个 [n] 都落在真实资料编号内、误拒答检测；评测侧：引用可验证率 1.0（25 题）。
Q9 Replan 为什么只做一轮？
防循环烧钱：重规划自身也可能失败，一轮后仍有降级就走聚合器降级文案 + 前端 warning， 保证"总有产出、绝不悬挂"。轮数是配置，不是玄学。
Q10 MCP 与 Function Calling 什么关系？
FC 是模型侧机制（决定调哪个函数与参数），MCP 是应用侧接入协议（工具发现/连接/暴露）。 我的 MCP Server 与内部 Agent 共享 ToolRegistry：内部走 FC 循环，外部宿主走 JSON-RPC， 同一份工具实现。
Q11 指标为什么不用 LLM 裁判？
裁判有偏差且烧钱；must_contain/工具命中/拒答行为/引用编号四件事规则判 100% 可靠、 零成本、可回归。评测成本省下的同时把"裁判是否靠谱"这个不确定性消掉了。
Q12 最大的坑？
"拒答"与"诚实说明信息不足"的边界：早期评测把"未能查询到 X"误判成拒答（误拒率虚高）， 后来把口径拆开——拒答=职责外/库外，信息不足=部分完成。评测口径本身就是设计对象。
Q13 这不就是调一个 API 吗？（高频质疑，先给 30 秒版再展开）
30 秒反击："调 API 解决的是模型会说，Agent 解决的是系统做对。API 调用 只占我代码的 llm.py 一个文件、不到 100 行；剩下几千行解决的全是 API 不给你的问题： 模型输出不可靠怎么办、钱怎么不白烧、错了怎么恢复、效果怎么回归。就像问'你的网站不就是 发 HTTP 请求吗'——请求谁都会发，难的是高并发下的系统设计。"
第一层（不确定性管理）：Planner 拆 DAG → 同层并行 → 降级时带失败证据 Replan 换路径 重拆 → Reflector 五项确定性规则自检（引用编号/超预算/编造库外/误拒答/答非所问）→ 修复。 重试退避、超时降级、结果缓存、危险工具确认闸——没有一个概念属于"API"。
第二层（成本与上下文）：工具按 task_type 预加载省 16-28% token（25 题两轮对照实测）； 记忆四分类（滑窗摘要/Session State/跨会话画像/知识库）——API 是无状态的，"越用越懂你" 必须自己建；JSONL trace + 分步 token 归因，能回答"钱花在哪个环节"。
第三层（可验证性，分水岭）：25 题任务完成率 100%、引用可验证 96%，规则判定、 一条命令复现——API 调用没有回归测试的概念，Agent 没有评测闭环就是玄学。
基线对照实测（benchmark_report.md）：同 25 题，纯 API 直接调用（无工具/无知识库/ 无编排）任务完成率 0.48、拒答正确 0.84——推荐类 5 题全灭（编造"华为 FreeBuds 6i 约 399-499 元"这类商品池外商品）、4 道拒答题全硬答。Agent 用 15 倍 token 买到的正是 不编造、可溯源、该拒绝就拒绝。"API 便宜但不可信，Agent 贵得有道理。"
